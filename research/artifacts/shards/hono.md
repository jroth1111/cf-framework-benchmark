### hono

#### Findings
- **[hono-F01]** This repo’s Hono app is currently a minimal Worker app on `hono@^4.12.5` with no JSX or SSR path implemented, which makes bundle size, startup time, and any future HTML rendering strategy the main optimization levers. — Confidence: MEDIUM — [Hono presets](https://hono.dev/docs/api/presets) [SINGLE-SOURCE] — As-of: Hono 4 docs
- **[hono-F02]** On Cloudflare Workers, Hono recommends the default `hono` preset for post-boot routing speed, but provides `hono/tiny` as a smaller-bundle option using `PatternRouter`; for a very small benchmark route set, `hono/tiny` is worth testing because bundle and startup size may matter more than advanced router throughput. — Confidence: HIGH — [Hono presets](https://hono.dev/docs/api/presets) + [Routers](https://hono.dev/docs/concepts/routers) — As-of: Hono 4 docs
- **[hono-F03]** If benchmark pages can be prebuilt, Hono’s `toSSG` / `onlySSG` path combined with Cloudflare Workers Static Assets removes per-request SSR and is the cleanest way to cut Worker CPU and client work for read-only pages. — Confidence: HIGH — [SSG Helper](https://hono.dev/docs/helpers/ssg) + [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/) — As-of: Hono docs / Cloudflare docs current
- **[hono-F04]** If pages must stay dynamic, Hono supports streaming SSR via `jsxRenderer(..., { stream: true })` and `renderToReadableStream()` with `Suspense`, allowing the shell to flush before slower async subtrees resolve and improving early delivery for dynamic pages. — Confidence: HIGH — [jsxRenderer middleware](https://hono.dev/docs/middleware/builtin/jsx-renderer) + [Hono JSX guide](https://hono.dev/docs/guides/jsx) — As-of: Hono 4 docs
- **[hono-F05]** Streaming JSX is not free on the client: Hono documents `StreamingContext` for adding a nonce to scripts generated by `Suspense` / `ErrorBoundary`, which implies streamed suspense boundaries inject patching scripts; for simple benchmark pages, static HTML or full HTML responses are likely lower client CPU/memory than overusing streamed suspense boundaries. — Confidence: MEDIUM — [Hono JSX guide](https://hono.dev/docs/guides/jsx) [SINGLE-SOURCE] — As-of: Hono 4 docs
- **[hono-F06]** The plain `hono/html` helper is a lower-overhead rendering option for mostly static HTML pages because it avoids the richer JSX renderer/runtime features; for benchmark pages with no interactivity, this is a credible minimal-overhead path. — Confidence: MEDIUM — [HTML Helper](https://hono.dev/docs/helpers/html) [SINGLE-SOURCE] — As-of: Hono 4 docs
- **[hono-F07]** Middleware cost matters in Hono because middleware runs in registration order and can be scoped per path; the docs explicitly support path-scoped middleware, so hot HTML routes should avoid broad global middleware. — Confidence: HIGH — [Middleware guide](https://hono.dev/docs/guides/middleware) — As-of: Hono 4 docs
- **[hono-F08]** `compress()` is unnecessary on Cloudflare Workers because response compression is automatic, so enabling it on benchmark routes adds no value. — Confidence: HIGH — [compress middleware](https://hono.dev/docs/middleware/builtin/compress) — As-of: Hono 4 docs
- **[hono-F09]** `contextStorage()` uses `AsyncLocalStorage` and requires `nodejs_compat` or `nodejs_als` on Workers; for benchmark paths, avoiding it prevents unnecessary runtime expansion and likely overhead. — Confidence: HIGH — [contextStorage middleware](https://hono.dev/docs/middleware/builtin/context-storage) + [Cloudflare compatibility flags](https://developers.cloudflare.com/workers/configuration/compatibility-flags/) — As-of: current docs
- **[hono-F10]** Hono cache middleware on Workers depends on the Cache API and is only usable on custom domains; Cloudflare’s Cache API is per-data-center and `cache.put` is incompatible with tiered caching, so header-driven CDN caching or Static Assets is usually safer and more comparable for benchmark HTML. — Confidence: HIGH — [cache middleware](https://hono.dev/docs/middleware/builtin/cache) + [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/) — As-of: current docs
- **[hono-F11]** Cloudflare Workers still have a 128 MB isolate memory limit and recommend streaming APIs to avoid buffering large responses; Cloudflare’s January 2025 streamed `HTMLRewriter` replacement support reinforces that streamed transforms are preferred over buffered post-processing. — Confidence: HIGH — [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) + [HTMLRewriter](https://developers.cloudflare.com/workers/runtime-apis/html-rewriter/) + [Cloudflare changelog: streamed HTMLRewriter replacement](https://developers.cloudflare.com/changelog/post/2025-01-31-html-rewriter-streaming/) — As-of: current docs / 2025-01 changelog

#### Recommendations
- Prefer static generation for read-only benchmark pages by using Hono SSG plus Workers Static Assets; keep only APIs or truly dynamic content in the Worker.
- If dynamic HTML is required, stream only a small number of genuinely slow subtrees and keep the outer page simple; do not introduce many suspense boundaries on simple pages.
- For server-only benchmark pages, choose `hono/html` or server-only JSX and ship zero client hydration JS.
- A/B test `hono` versus `hono/tiny` in this repo because the route table is small enough that startup/bundle size may dominate.
- Remove global middleware from hot HTML routes and never enable `compress()` on Workers routes.
- Avoid `contextStorage()` and Node compatibility flags on benchmark paths unless a measured requirement appears.
- Prefer cache headers or Static Assets before introducing Hono cache middleware.
- If HTML needs edge mutation, use streamed `HTMLRewriter` instead of building full HTML strings in memory.

#### Risks
- `hono/tiny` changes the router implementation, so route-matching tradeoffs may appear if the app grows more complex.
- Streaming JSX can improve TTFB but still add client-side patch scripts and error-handling complexity.
- Hono streaming helpers have different error semantics once output has started.
- Hono cache middleware behavior differs between `workers.dev`, preview, and custom-domain environments.
- Static generation only fits routes whose dynamic and personalized behavior can be separated cleanly.

#### Gaps
- No recent Hono-maintained benchmark quantifies `hono` versus `hono/tiny` on modern Workers cold starts for HTML workloads.
- No primary source quantified the client CPU cost of Hono suspense patch scripts.
- This repo has no JSX/SSR implementation yet, so the best rendering path still needs direct in-repo measurement.
